GERIMMO V1 — PROCÉDURE À EXÉCUTER UNIQUEMENT APRÈS AUTORISATION HUMAINE
Aucune étape extérieure de cette procédure n’a été exécutée pendant la mission.

1. CONDITIONS AVANT TOUT PUSH / FUSION / DÉPLOIEMENT
Autorisation explicite portant sur les SHA de COMMITS.txt, FICHIERS.txt, les sept SQL de MIGRATIONS.txt et une fenêtre de maintenance ciblée. Ne pas intégrer les retouches UI préexistantes de la copie corrections-prioritaires.
Reconfirmer main, SHA public et historique SQL : référence observée le 10/11, 35b2a1258eca30dde66d31bceb5f77748a8f9ab0. Si divergence, arrêter pour comparer uniquement le nouveau delta.
Accès Vercel administratif indispensable : identifier les déploiements et leurs SHA, les alias secondaires accessibles, les variables réelles, la cadence cron et la durée maximale autorisée. Confirmer qu’une fusion dans main NE promeut PAS automatiquement le candidat. Ne jamais supposer ce réglage acquis : l’accès administratif précédemment essayé répondait 403.
Vérifier GitHub gerimmo-production : approbateur obligatoire distinct de l’auteur, branche protégée, secrets de publication accessibles uniquement au contrôleur approuvé.
Faire réussir la CI complète hébergée sur les SHA main exacts après intégration autorisée, sans neutraliser une garde. Cette CI n’a pas été lancée depuis la copie locale sans remote.
Sauvegarde existante confirmée : 10/11/2026 08:33:27 UTC, préfixe 20261110-0829, zéro échec. Exécution GitHub déjà vérifiée 42782927608. Au moment de publier, une nouvelle sauvegarde de moins de 90 minutes est obligatoire. L’ancienne est désormais trop ancienne pour franchir la garde.
Démontrer l’accès aux archives chiffrées et à la clé de déchiffrement, la couverture Auth et stockage, ainsi que l’accord d’un opérateur de restauration. Les restaurations fictives locales ne prouvent pas la restauration complète des données réelles. Aucune restauration réelle ne doit être tentée pour « vérifier » sans décision séparée.

2. CONFIGURATION COMMERCIALE À VÉRIFIER, PAS APPLIQUÉE ICI
GERIMMO_MODE=commercial ; VERCEL=1 ; VERCEL_ENV=production ; NEXT_PUBLIC_SITE_URL=https://www.gerimmo.app.
GERIMMO_PILOTE_LIMITE ne doit pas valoir true ; GERIMMO_PAIEMENTS_DESACTIVES ne doit pas valoir 1 ; GERIMMO_PREPRODUCTION_VALIDEE ne doit pas valoir 1.
COURRIELS_CHIFFREMENT_CLE : clé durable de 32 octets encodée sur 64 caractères hexadécimaux. La conserver sauvegardée ; ne pas la faire tourner sans migration du contenu chiffré. Les clés réelles Stripe, les Price IDs, droits, essais et abonnements existants restent inchangés.
Vérifier CRON_SECRET, clé de service et secrets de webhooks existants. RESEND_WEBHOOK_SUIVI_SECRET et raccordement signé pour les preuves de livraison ; « accepté » ne signifie pas « livré ».
La liste des courriels autorisés est fermée dans le code, indépendante des paiements. Aucun drapeau commercial ne réactive les circuits non qualifiés. Ceux-ci restent visibles en supervision et nécessitent une démarche humaine maîtrisée, sans prétendre que l’e-mail est parti.
GERIMMO_TRANSITION_LOTS=maintenance active la maintenance ciblée. Ne pas utiliser le drapeau pilote pour obtenir cette maintenance : il couperait aussi les paiements.

3. TRANSITION EN DEUX VERSIONS, SANS ANCIEN WORKER ACTIF
Préparer d’abord la branche codex/transition-v1 (base publiée + cinq fichiers de maintenance), faire contrôler son SHA main puis la publier via le contrôleur existant après approbation. Schéma encore ancien : retour applicatif possible à cette étape seulement.
Activer sa maintenance ciblée dans le déploiement approuvé. Vérifier /api/sante : bon SHA et maintenance=true ; les POST métier et cron factures doivent répondre 503 avec indication de reprise. Stripe webhook, suivi Resend, webhook signature et la mission abonnements ne sont pas bloqués par le proxy de maintenance.
Interdire l’accès aux anciens déploiements/alias capables de traiter en arrière-plan. Arrêter leurs déclencheurs non financiers et attendre la fin de leurs exécutions : durée supérieure à maxDuration de tous les jobs et au délai maximal des appels fournisseur, à établir sur la configuration réelle. Un ancien alias encore exécutable empêche la bascule.
Appliquer, sous contrôle opérateur, scripts/deploiement/transition/fermer.sql. C’est une opération de maintenance explicite, hors des sept migrations. Elle gèle douze tables métier ; les organisations, abonnements, événements Stripe et écritures financières ne sont pas gelés. Elle est rejouable.
Attention : un retour Zoho pouvant modifier demandes_signature peut recevoir une erreur pendant le gel SQL. La conservation/reprise de cet événement devra être confirmée chez le prestataire avant d’ouvrir la fenêtre ; sinon attendre l’absence de signatures en cours ou suspendre la bascule. Ne pas prétendre à une garantie fournisseur testée localement.
Relever les traitements en cours/incertains, attendre la fin des transactions et conserver leurs identifiants. Aucun import automatique des anciens événements déjà envoyés. Les sept migrations ne réémettent pas cet historique.

4. MIGRATIONS ET CANDIDAT FINAL
Intégrer la branche de livraison approuvée dans main avec promotion automatique désactivée et CI verte sur le SHA exact. Préparer le candidat en production sans alias public, maintenance=true. Les démarches main/push restent interdites jusqu’à autorisation.
Utiliser le chantier migrations.yml existant, avec UNIQUEMENT les sept noms de MIGRATIONS.txt dans leur ordre. D’abord simulation, puis application expressément approuvée. Ne jamais utiliser un « db push » global sur cette base aux historiques renommés.
Le conditionneur vérifie les SHA256 originaux, retire uniquement leur enveloppe BEGIN/COMMIT externe, puis applique les gardes syntaxiques existantes. Le workflow exécute les sept corps dans UNE transaction, conserve les sources originales dans l’historique et refuse tout fichier déjà appliqué. Toute erreur annule le lot entier. Aucun fichier pilote dans supabase/migrations ; le profil local est aussi interdit par nom et contenu dans le conditionneur commercial.
Après commit SQL : vérifier les sept versions, leurs empreintes, RLS/journaux, huit triggers notification_transactionnelle et absence de securite_instance_pilote / verrou_paiements_pilote. Ne pas désactiver les captures pour forcer un résultat.
Publier le candidat maintenu avec publication-controlee.yml : base_compatible=false, correction_en_avant=true, revision_transition=SHA MAIN EXACT de la transition actuellement publiée. Le contrôleur refuse si l’une des deux versions ne déclare pas maintenance=true, si la CI/SHA ne correspond pas, ou sans approbateur. Il ne retournera JAMAIS automatiquement à l’ancienne version dans ce mode.
Après promotion, vérifier les trois contrôles de santé, l’accès, les droits et les événements Stripe en lecture. Maintenir le gel SQL tant que la version finale n’est pas confirmée. Appliquer ouvrir.sql, puis préparer/promouvoir la même version applicative sans maintenance. Pour cette seconde promotion, ancienne et nouvelle versions utilisent le même schéma V1 : le retour compatible peut viser le candidat V1 encore en maintenance, jamais le code 35b2a12.
Reprendre progressivement les tâches autorisées. Confirmer la cadence /api/cron/factures chaque minute et la capacité réelle d’hébergement avant de promettre un délai de cinq minutes.

5. SURVEILLANCE / ARRÊT / CORRECTION EN AVANT
Contrôler à la bascule, à 5 minutes, 30 minutes et le lendemain : SHA, santé, erreurs 5xx, file factures, intentions de notifications, messages inconnus/à vérifier, webhooks Stripe en attente et absence de double imputation. Utiliser la supervision déjà livrée ; ne pas diffuser les contenus/adresses dans les journaux.
Arrêt immédiat : paiement ou webhook bloqué, accès inter-organisation, double traitement, document incorrect, capture empêchant une écriture normale, absence de chiffrement ou ancien worker encore actif.
Après installation SQL, garder le nouveau schéma et les journaux. Si défaut : maintenir/réactiver la maintenance ciblée et fermer.sql, préserver les événements Stripe ; corriger EN AVANT sur ce même schéma avec tests et nouveau SHA approuvé. Le contrôleur signale intervention_requise, sans rollback automatique en mode correction en avant. Ne pas cocher une fausse compatibilité pour contourner cette garde.
Avant commit SQL seulement, rollback transactionnel complet testé. Après commit, les signatures SQL anciennes sans réservation ne fonctionnent plus : redéployer simplement 35b2a12 n’est pas un retour sûr. Supprimer les journaux ou restaurer une ancienne base ferait perdre des opérations légitimes ; ce n’est pas la procédure de retour.
Aucune réémission automatique d’un e-mail incertain. Rapprocher les preuves fournisseur ; à défaut conserver l’incertitude et solliciter un opérateur. Le fournisseur détermine les garanties effectives de livraison et d’idempotence.
